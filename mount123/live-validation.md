## 发现并修复的问题

首次进入大 ZIP 返回 EIO，日志指向非 UTF-8 文件名。独立检查发现 797 个条目均使用可解码为 GB18030 的旧编码，没有危险路径。补齐文件名解码后，原归档目录读取和成员完整内容比对通过。

新增回归测试从 ZIP 字节经过解析到 FUSE Lookup，覆盖旧中文编码、CP437 以及带 CRC 的 Unicode Path 扩展字段。仅改变显示路径；原始 ZIP 名称保留供内容读取与缓存键使用，路径安全校验仍在解码后执行。

本次验证覆盖普通文件、单卷非加密 ZIP 的 Store/Deflate 成员；不是对全部账户文件、全部编码、加密或分卷归档的兼容性承诺。未向网盘上传、修改或删除文件。验收结束后卸载临时挂载点。

## 共享元数据缓存与取消修复后的复验

同日使用 `-metadata-mib 4 -directory-ttl 5s -source-ttl 30s` 连接真实账户重新挂载：

- 根目录仍为 26 项；超过 5 秒后重新访问成功。
- 普通文件三个偏移的读取与独立 API Range 请求逐字节一致。
- 原 5.82 GB ZIP 可浏览 796 个文件（另外 1 个条目为目录）。完整读取同一个 Store 成员，SHA-256 与首次验收记录一致，重复打开内容一致。
- 原 Deflate 成员完整内容与独立 Python ZIP 解压结果一致，重复打开成功。
- 内核仍显示只读；测试结束后已卸载，没有远端写入操作。

本地回归另验证：阻塞 4 MiB Deflate 成员的中间压缩块时，取消 Open 会在 1 秒测试期限内返回 EINTR，并终止 HTTP 请求，随后可重新打开；旧 Open 请求的取消不影响后续 Read；ZIP 子目录在索引过期后可重建；父目录刷新到新版本后，新路径读取新内容而旧成员保留旧快照；CRC 错误会被拒绝。

并发缓存测试覆盖同键合并、仅一个构建槽时发起者取消后等待者接管、LRU/TTL、超预算显式失败，以及文件 inode 不持有整个 ZIP 中央目录。ZIP32/ZIP64/自解压前缀的有界预检和超限/截断测试通过。完整 `MOUNT123_FUSE_TEST=1 go test -race ./...`、`go vet ./...` 通过。
