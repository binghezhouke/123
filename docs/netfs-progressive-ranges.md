# Progressive network range reads

Remote reads now copy requested bytes from an in-progress HTTP Range response as soon as those bytes have reached the cache staging file. The staging area is a private temporary file; response bytes are not accumulated in a caller-sized heap buffer. A read that needs only a small prefix can return while the same shared range task continues to validate and publish the full response.

The persistent cache only exposes an extent after the response has passed the existing status, `Content-Range`, entity validator, exact body length, and trailing-byte checks, and after durable Sync, close, and atomic rename succeed. A short or overlong body, changed entity, cancellation, or write/publication error never becomes a complete cache entry. Bytes already delivered from a valid response prefix cannot be retracted if a later body check fails; a later read beyond that prefix observes the flight error and the failed extent remains absent. Archive-member end and checksum validation still run in the archive layer and are unchanged.

Each cache owns two independent schedulers. The HTTP scheduler bounds active response bytes and request slots. The staging scheduler bounds bytes being downloaded or waiting for cache publication, and keeps its reservation through Sync and rename. Both use the configured `DownloadConfig` limits and foreground reserve. A shared range flight owns one priority object; promoting it wakes queued acquisitions in both schedulers. HTTP and staging budgets have separate locks, so holding a staging reservation while waiting for an HTTP slot cannot deadlock against publication.

If an extent exceeds the background share of the staging budget, the cache processes it as sequential extents no larger than that share. Foreground work can use the full configured staging budget. The HTTP client still requests the largest range allowed by the active extent and the existing request chunk setting. Reads larger than the cache continue by copying each completed extent into the caller's buffer before fetching the next chunk, so cache eviction cannot make the reader refetch earlier bytes.

Overlapping readers join a flight only when it covers their next unread offset. If another active flight begins later, the reader first fills the uncovered prefix and then joins the later flight. One canceled reader releases only its own reference. Foreground consumption may keep the shared task alive through publication; a background-only task with no remaining readers is canceled. Published staging files stay pinned in the cache until the flight's readers release their references, so an open progress file cannot evade the cache's disk accounting.

## Baseline comparison

The previous read path waited for the complete selected HTTP Range and cache publication before returning any requested bytes. For a cold ordinary read this meant waiting for the full 1 MiB read-ahead extent; for the 16 MiB range-window path it meant waiting for all 16 MiB. The new path returns after the target prefix is written, while the HTTP request and full validation continue in the background. The deterministic test `TestRemoteReadReturnsPrefixBeforeRangeTailAndPublishesAfterward` blocks the tail after sending 4 KiB and verifies that an 8-byte read returns before the tail is released. Its verbose output records the local first-read latency; exact elapsed time depends on the host and is not treated as a performance guarantee.

Progressive delivery changes latency, not the bytes required to fill a complete cache extent. `TestProgressiveFirstReadLatencyAndDownloadedByteBaseline` uses a local source that pauses 40 ms after its first 4 KiB. Across three runs, the previous full-fill behavior took about 41.3 ms before the 8-byte read could proceed; progressive reads returned in about 0.24–0.28 ms. Both paths downloaded 1,048,577 response bytes: the one-byte entity probe plus the same full 1 MiB Range. These are local deterministic-fixture measurements, not production-network benchmarks. A caller that cancels before consuming a prefix does not retain a background task; a foreground caller that consumes a prefix permits the bounded task to finish and publish. `DownloadStats` reports active and peak staging bytes separately from active HTTP response bytes.

The public Remote tests cover prefix-before-tail delivery, slow durable publication, restart reuse, incomplete and overlong body rejection, overlapping and interleaved readers, owner cancellation with another reader still active, and reading larger than cache capacity. Tests use local HTTP servers and do not mount a live filesystem.
