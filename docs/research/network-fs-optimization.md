# 网络文件系统优化建议汇总

调研日期：2026-10-09。本文把 NFS、SMB3、rclone VFS、JuiceFS、S3FS、goofys、Mountpoint for Amazon S3 和 SeaweedFS 的公开实现与文档，映射到 `mount123` 的 Linux 只读 FUSE 场景。

详细资料分为三部分：[缓存与一致性](network-fs-optimization-cache.md)、[预取与随机读取](network-fs-optimization-prefetch.md)、[韧性与请求治理](network-fs-optimization-resilience.md)。

## 当前已经覆盖的能力

当前实现已经采用了主流网络文件系统的几个核心原则：

- 目录列表、密码侧车、改名归档探测和归档索引都有按身份共享的缓存；目录快照可以持久化，过期时先服务旧快照并后台刷新。
- Range 数据按账号、文件 ID、版本、大小和验证器隔离，下载中的相同范围会合并；直链只在进程内复用，不落盘、不写日志。
- 普通文件有消费驱动的字节预读，图片有按浏览方向的文件级预取；前台读取可以加入已有后台请求，预取和前台共享请求与字节预算。
- 缓存有容量、保留等级、打开文件保护和恢复统计；归档索引与解压结果也进入持久缓存，但密码和短期直链不进入持久缓存。
- 控制 socket、`.mount123-refresh`、`.mount123-probe` 和 `doctor` 提供了显式刷新、探测和诊断入口；挂载保持只读，网络故障使用有界重试。

这些做法分别对应 NFS 的属性/目录缓存、SMB 的请求额度与 lease 缓存、rclone 的稀疏 VFS 缓存、JuiceFS 的多级数据缓存，以及 Mountpoint S3 的并行 Range 与退避。协议层的 lease 本身没有被伪造，因为 123 的 HTTP API 没有服务器回调来撤销客户端缓存。

## 优先级建议

### P0：按 API 类型和父目录治理请求

当前下载请求已经有独立的并发数和在途字节预算，但目录列表、单项详情、直链解析和 Range 下载应继续分开计数和限流。建议增加按账号/API 地址的令牌桶，并对同一父目录的并发列表构建设置小额度；`find`、多个终端和后台探测共享这一额度。

应记录每类请求的排队时间、实际耗时、429 次数、`Retry-After` 等待、重试次数和失败原因。这样可以判断是 123 API 限流、网络延迟还是本地缓存不足，而不是简单降低所有并发。Mountpoint S3 的并行操作数、吞吐和分片大小分开控制，SMB 的 credit 也在发请求前计算成本，可作为设计参考。

### P0：增加短期负缓存

对确定的 `ENOENT`、已确认不是归档的探测结果和永久无效路径增加 1–5 秒的内存负缓存，可以减少文件管理器反复 `Lookup`/`stat` 造成的无效请求。超时、429、5xx、断线和权限错误不能进入负缓存。

目录刷新、探测结果发布、密码侧车上传和归档别名安装必须按父目录主动失效负缓存。FUSE 负 dentry TTL 应保持在秒级，不能复用 24 小时云目录 TTL；否则新生成的 `.7z` 别名或 `.pwd` 会被旧的不存在结果遮蔽。JuiceFS 明确把 negative-entry cache 与目录/属性缓存分开，适合参考。

### P1：相邻 Range 的短窗口合并

现有缓存键和 flight 合并边界应保持不变。在同一内容身份内，对于短时间内相邻且尚未发出的范围，可以合并成一个请求；已发出的 HTTP 请求不抢占，只影响后续排队请求。合并窗口应受最大读放大和前台延迟约束，并通过“实际消费字节 / 下载字节”和重复下载字节验证收益。

顺序读取继续使用消费反馈扩大窗口；远距离 seek、预取未消费量过高、缓存盘拥塞或命中率下降时收缩。rclone 的 `read-wait` 说明轻微乱序时可以短暂等待顺序范围，但真正随机访问必须快速放弃等待。

### P1：把断线状态分层暴露

`doctor` 和 `io-stats` 可以进一步区分：旧目录快照仍可用、已缓存 Range 可读、需要联网验证来源、直链失效等待刷新、目录刷新失败。统一使用带抖动的指数退避并尊重 `Retry-After`，但保留交互式操作的总时限；NFS 的 hard mount 无限重试不适合当前终端浏览。

### P2：无版本信息时的内容摘要

继续优先使用 123 File ID/版本、大小和强 HTTP 验证器。只有来源没有可靠版本身份时，才考虑对已读取块记录摘要，或在完整成功后保存摘要索引；默认对大文件做全量 SHA-256 的成本高，也不能替代服务端版本信息。

### P2：分层缓存自适应

保留内存元数据、磁盘 Range/索引和内核 FUSE 缓存的三层结构。只有当统计显示热点反复淘汰时，才考虑增加共享缓存或单独的解码块缓存；共享缓存必须包含账号/API、内容版本和密码身份，不能保存短期直链。ObjectiveFS 和 JuiceFS 的多级缓存说明了层次划分的收益，也提醒缓存目录应放在本地可靠磁盘上。

## 不建议直接移植

- NFS delegation、SMB oplock/lease：需要服务器授予和召回，123 HTTP 后端没有等价通知。
- NFS hard mount 的无限重试：会让交互式 `ls`、`file` 或 `cd` 长时间无响应。
- 默认全文件预取或固定大块：对归档内随机图片和稀疏读取会产生严重读放大。
- 把目录 TTL、数据 TTL、直链过期时间设成同一个值：三者分别对应命名空间新鲜度、不可变内容身份和授权 URL，有不同的失效条件。
- 跨账号共享 Range 或解压缓存：容易造成内容、密码或权限身份混淆。

## 建议的验收指标

后续实现前应先从 `io-stats` 增加或确认这些指标：

| 指标 | 目的 |
| --- | --- |
| 每类 API 的请求数、排队时间、429 和 Retry-After | 判断目录遍历是否打满平台 API |
| 负缓存命中、失效、刷新后误命中 | 验证短 TTL 是否减少无效 Lookup |
| Range 合并等待人数、重叠字节、重复下载字节 | 衡量相邻请求合并是否降低读放大 |
| 直链解析/复用/401/403/404/410 | 调整 URL 复用和提前刷新策略 |
| 旧快照服务、磁盘恢复、刷新失败 | 判断断线时用户仍能访问哪些内容 |
| 预取计划、实际命中、未消费字节和淘汰后重取 | 调整图片预取与字节预算 |

建议在 5/50/150 ms RTT、50/250 MB/s 限速、冷缓存/热缓存/重启缓存、顺序读/随机 seek/多文件混读下测量 P50/P95/P99 延迟、有效吞吐、请求放大和缓存占用，再决定是否实施 P0/P1 项。
