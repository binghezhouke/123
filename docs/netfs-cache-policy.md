# Network filesystem cache retention policy

The disk cache still has one hard byte limit. Reservations count toward that limit before a fill starts, pinned entries cannot be evicted, and a fill returns `ENOSPC` if no unpinned victim can make enough room. Cache class changes do not change the byte limit or publication, cancellation, and pin semantics.

Entries use four retention classes. Eviction picks the least recently used unpinned entry from the lowest available class, in this order:

1. `speculative`: data filled by work marked `workqueue.Background`, including read-ahead and prefetch.
2. `probation`: foreground data on its first use, or data that was prefetched and later consumed.
3. `hot`: data that a reader revisits or accesses outside a single forward or reverse pass through its range.
4. `index`: complete persisted archive indexes within the protected-index share.

The first foreground use of a speculative entry promotes it to probation. A foreground fill also starts in probation. The cache tracks a small in-memory scan direction and high-water interval per entry: consecutive reads that move forward or backward keep the entry in probation; revisiting an already-consumed interval promotes it to hot. This lets a single large scan age out earlier scan data without immediately giving every range hot retention. The interval is deliberately approximate and resets after restart.

Archive indexes receive a protected share of `cache limit / 8` by default, with no fixed byte ceiling, and `-index-budget-mib` sets it independently. Ordinary range data and speculative prefetch cannot consume that reservation: a metadata object enters the index class only while the share has room. An object that no longer fits is demoted to probationary data rather than displacing an index that is already protected, so it stays readable and is reclaimed later as ordinary LRU data. Demotion is the documented response to an exhausted share; removing a still-protected object only happens as the last resort after speculative, probationary and hot entries, and is recorded as a capacity eviction. Reopening a cache whose persisted share exceeds a smaller configured budget trims protected objects oldest-first, and those restore-time demotions are counted so an operator can see that a budget change pushed an index out of protection.

The class is encoded as a one-letter suffix in the already opaque hashed cache filename (`.s`, `.p`, `.h`, or `.i`). A protected index object carries a second letter naming its family, because the file name is the only thing that survives a restart: `.ia` archive index, `.id` directory snapshot, `.ir` remote identity descriptor, `.ib` archive probe record, and `.iu` for objects whose family is unknown. A pre-family `.i.blob` object still loads as a protected, unclassified index. The suffix contains no cache key, account identity, URL, or password. The in-memory scan interval is not persisted. Existing ordinary `.blob` entries and legacy range-extent names load as probationary entries and are upgraded on real use; they do not need manual removal. Archive index reads use the explicit index API so loading metadata does not make it a content hot spot.

Durable caches preserve class suffixes across process restarts. Ephemeral caches use the same admission and eviction decisions inside their per-process directory, then remove that directory on close; stale ephemeral directories are removed on later startup as before. No cache class or index-share state is stored outside the cache files.

`mount123/internal/storage/cache_policy_test.go` exercises the public `Cache`, `Remote.ReadAt`, and archive-index cache APIs with a local HTTP Range server. It warms a repeated image and a small index, scans more data than the cache can hold using 64 KiB reads, then checks that old scan data is evicted, the image and index remain reusable, capacity stays bounded, and durable restart preserves the classes. It also verifies that an index beyond the protected share still enters the ordinary cache class when the total budget allows.

Eviction keeps one LRU queue per retention class, so it examines unpinned entries in the speculative queue first and stops as soon as it finds a victim. A local microbenchmark with 20,000 entries (one oldest speculative entry and 19,999 hot entries) measured 609,738 ns/op on the original full-table priority scan and 7,524 ns/op with class queues, about an 81x reduction. Reproduce from `mount123` with `GOTOOLCHAIN=local GOPROXY=off /tmp/123-go-sdk/go/bin/go test -run '^$' -bench '^BenchmarkEvictFindsRareSpeculativeEntryAmongHotCache$' -benchtime=100x -count=1 ./internal/storage`. The runs used Go 1.27.1 on Linux `7.0.14-19-pve` x86_64 with an AMD Ryzen 5 5600G. This isolates victim selection; it does not measure filesystem removal latency or a full remote workload.

## Per-source retention

Mount and standalone serve enable `-cache-file-percent=20` by default; `0` disables it and values from 1 to 100 select a percentage of the global capacity. At the default 50 GiB capacity, each remote file gets a 10 GiB retained data share. A scoped HMAC digest of the account/API identity and stable file ID groups its raw extents, decoded members, nested archive blocks and solid-group objects together. Derived metadata continues to use the separate index policy. Individual remote volumes have their own raw-data identities; decoded content belongs to the archive entry source.

Before reserving a fill, reclaim that source's own unpinned entries in the same class/LRU order, then apply the global admission limit. Each source has its own class queues; victim selection does not scan unrelated files. Reservations participate in source accounting. This is a retention limit, not an active-read hard limit: pinned objects and active reservations may exceed the source share, but release and retained-fill publication trim reclaimable excess. The global hard limit remains in force, so active readers can still cause global pressure and `ENOSPC`. Prefetch stops if successfully fetched data cannot remain resident instead of repeatedly re-downloading an immediately evicted extent.

With streaming enabled, an archive member larger than half the source share uses the existing demand/block decoder, including at the archive root. The remainder leaves room for compressed input and nested layers. Solid-group retention is bounded by one quarter of the source share; raw windows and nested blocks also respect it. This does not make solid formats independently seekable: decoding a later member can still require its prefix. Explicit strict mode (`-stream-members=false`) keeps its existing full-member verification contract and may temporarily exceed the per-source share while a member is pinned.

Durable filenames append an opaque `.o<32 hex characters>` ownership suffix before `.blob`; no source ID, name or URL is exposed. Restore reads the suffix and enforces the share before serving requests. Legacy range names already identify their source and can be accounted immediately; the tree binds them to the stable cloud-file owner without downloading them. Legacy decoded objects without ownership are adopted on access and otherwise remain under the global limit until normal eviction. Their remaining size is observable as `unattributed_data_bytes`; upgrading never flushes the cache.

`/status`, the status API and I/O snapshots expose `source_limit_percent`, `source_limit_bytes`, `source_count`, `largest_source_bytes`, `largest_source_reserved_bytes`, `source_over_limit_count`, `source_evictions`, `source_eviction_bytes`, and `unattributed_data_bytes`. The two largest-source fields describe the same source, selected by resident plus reserved bytes; they contain no identifying data.

There is no universal per-file percentage. The 20% default leaves capacity for roughly five source working sets (subject to the separate metadata share and active pins). It is deliberately adjustable. [Linux bcache](https://docs.kernel.org/admin-guide/bcache.html) avoids cache pollution by bypassing large sequential I/O, and [Caffeine's design](https://github.com/ben-manes/caffeine/wiki/Design) separates admission and frequently reused data. Those support the anti-pollution policy; neither specifies this project's 20% ratio.

Synthetic tests cover same-source eviction while unrelated data stays warm, pins and reservations, failed and cancelled fills, durable owner restoration, legacy adoption, metadata protection, bounded prefetch under pressure, and root/nested archive random reads through both the service and FUSE node interfaces.

 Cache behavior is process-local while running, so an abruptly terminated process can lose the recent in-memory scan direction, while durable class suffixes remain intact.
